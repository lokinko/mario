# 长期记忆与记忆整理（dreaming）

## 解决的问题

[买点观察助手](buy-watch.md)的讨论和周末复盘跨越多次对话。没有记忆时，用户每次都要重复同样的沟通偏好（例如“先讲结论”“只看分红持续性”）和长期背景（例如“两年后需要一笔首付”），上一次讨论得出的、附带改变条件的判断也会丢失。长期记忆只解决这一障碍：把用户亲口说过的偏好与背景、讨论中形成且仍可能适用的观点，整理成可审阅的条目，供后续分析理解讨论方式。

记忆不是事实来源，不改写财务档案或账本，也不让模型更顺从用户。工作流如何使用记忆见[AI 问答工作流](ai-workflow.md#表述与不迎合)，授权边界见[AI 数据边界](ai-data-boundary.md)。

## 条目契约

条目保存在账号 schema 的 `analysis_memories` 表，契约归 [models/memory](../server/src/models/memory.rs)。

| 字段 | 约束 |
| --- | --- |
| `kind` | `preference`（讨论与沟通偏好）、`viewpoint`（有依据、写明适用条件的判断）、`context`（用户说明的长期背景） |
| `origin` | `userStated`（摘自用户问题原文）或 `modelInferred`（归纳自模型回答）；偏好与背景只能是 `userStated` |
| `statement` | 1–200 字的一句话陈述；用户倾向写成“用户倾向……”，不写成事实 |
| `rationale` | 1–300 字，说明为何保留、依据与适用条件 |
| `sourceAnalysisIds` | 1–3 个来源分析 ID，不重复 |
| `quote` | 1–200 字，必须逐字出现在所引分析中：`userStated` 只能摘自用户问题，`modelInferred` 可摘自问题或回答 |
| `active` | 归档后为 `false`，不再进入分析；可恢复 |

有效条目最多 60 条；同一陈述（规范化后）不重复保存。

## 分析时的选取

[context/memory](../server/src/context/memory.rs) 在冻结上下文时选取条目：

- 问答预设关闭“长期记忆”（`contextSelection.includeMemory=false`）时不选任何条目。
- 先放入最近更新的、用户亲口说明的偏好，最多 4 条。
- 只有财务档案、持仓与交易、研究证据三组全部开放时，才继续按与本轮及历史用户问题的字面相关度补充观点和背景，总数最多 10 条；任一资料组关闭时只保留偏好，因为观点与背景可能携带该组的个人信息。
- 进入模型的字段只有 `id`、`kind`、`origin`、`statement`、`updatedAt`，置于 payload 的 `memory.notes`，因此进入预览、指纹和冻结轨迹；理由与摘录不发送。

预览中“长期记忆”分组显示实际条数；`transparency.memoryNotesUsed` 记录本次使用数。系统策略要求偏好只说明怎样沟通，观点须按本轮资料重新检验，记忆不能作为事实引用，也不改变证据分量。

## 记忆整理（dreaming）

整理把已完成的分析沉淀为条目变更，由 [application/memory](../server/src/application/memory.rs) 编排：

1. 读取“已整理至”水位之后最早的最多 12 次分析（用户问题与回答前 1500 字）和全部有效条目，冻结为 `DreamInput`。
2. 释放账号锁，经与问答相同的模型配置和执行端口调用整理代理（[ai/dreaming](../server/src/ai/dreaming.rs)），最多 6 分 30 秒。代理只提出最多 8 项 `add`、`update`、`archive` 操作，格式错误至多修复一次。
3. 重新取锁，若期间条目被修改或已有其他整理推进了水位，返回冲突、不写入。
4. `screen_operations` 逐项确定性检查：长度与来源数、来源必须属于本批、摘录必须逐字出现、偏好与背景不得为模型推断、不重复、不超过有效上限、更新或归档的条目必须存在且每项只操作一次、归档须写理由。一项不合格只拒绝该项并记录原因，其余照常接受。
5. 在同一事务中应用通过的操作、推进水位，并保存本次摘要（读取分析数、新增、更新、归档与拒绝原因）。

整理代理的提示要求：只记录值得长期保留的内容，不记录一次性问题、行情价格、持仓金额与交易明细、模型给出的买卖建议、无依据猜测、恭维或情绪判断；用户多次表达同一倾向不会让它变成事实；新资料与旧条目冲突时以更新或归档修正，并写明是哪次分析推翻了它；分析与记忆本身都是不可信数据。

触发方式：

- 自动：问答完成后，若记忆开启且至少 3 次分析尚未整理，网页在后台发起一次整理；下一次提问先等待它结束。自动整理失败不打断问答，原因在记忆抽屉显示。
- 手动：在问答页“长期记忆”抽屉点击“立即整理”，只要有未整理的分析即可执行。

整理失败、超时或冲突都不推进水位，下一次整理会重新读取同一批分析。关闭记忆后不再整理，已有条目保留，可在抽屉中查看、归档或删除。

## 用户控制与接口

问答页的“长期记忆”抽屉按偏好、观点、背景分组显示条目，标明“你的原话”或“模型归纳”，展示理由、原文摘录与可打开的来源对话；每条可归档、恢复或永久删除，并显示上次整理摘要与被拒绝的整理建议。

| 接口 | 作用 |
| --- | --- |
| `GET /api/memory` | 条目、整理状态、未整理分析数、是否到期与记忆开关 |
| `POST /api/memory/dream` | 立即整理；返回更新后的概览 |
| `PUT /api/memory/{id}/status` | `{"active": bool}` 归档或恢复 |
| `DELETE /api/memory/{id}` | 永久删除 |

写入接口与其他账号写入一样要求 `If-Match`，不在[免版本检查例外](../server/src/http/policy.rs)中。

## 数据边界、备份与退役边界

- 整理会把历史问题与回答片段发送给当前配置的模型提供方；这些内容是当时已发送过的分析输入与输出，但整理时不重新按资料组过滤。不希望再发送时关闭“长期记忆”。
- 整理不读取账本、档案或研究原文，也不写入它们；条目只影响后续分析的上下文。
- 条目与整理状态（`settings[memory.dream_state]`）随账号个人备份导出，自同步数据集 v31 起包含；更早的备份没有该表，恢复后记忆为空、水位从头开始。schema 版本 18 建表。
- 早期的 `memory_preferences` 偏好表、`useMemory` 开关与 v7 多阶段工作流已退役，旧备份中的这些内容只校验并跳过，不迁入当前 `analysis_memories`；两者是不同的功能。

## 局限

相关度按字面二元组重合挑选，可能漏掉同义表述；模型归纳的观点可能有误，需要用户审阅与归档。条目没有自动过期，背景变化需要后续对话提供新依据才会被更新或归档。整理结果不证明观点正确，也不能替代原始资料核查。

## 实现与验证依据

[models/memory](../server/src/models/memory.rs) 测试覆盖逐字摘录、来源归属、模型推断偏好被拒、重复与上限、单项拒绝不影响其他项；[context/memory](../server/src/context/memory.rs) 覆盖偏好优先、相关度补充、授权缩小只保留偏好与关闭开关；[db/memory](../server/src/db/memory.rs) 覆盖事务应用、写入失败整体回滚、水位推进、备份往返、导入拒绝模型推断的偏好以及旧备份恢复为空记忆；[application/memory](../server/src/application/memory.rs) 覆盖到期判断、整理期间编辑返回冲突与关闭时拒绝；[ai/dreaming](../server/src/ai/dreaming.rs) 覆盖修复一次与两次失败报错。前端 [MemoryPanel 测试](../client/src/features/research/MemoryPanel.test.tsx)与 [Advisor 测试](../client/src/features/research/Advisor.test.tsx)覆盖抽屉操作、到期自动整理和下一问等待。真实模型的整理质量需单独评阅。
