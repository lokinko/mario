# 账户与端到端加密云同步

## 产品边界

账户用于识别用户与绑定设备，不改变 mario 的“本地优先”默认模式。只有用户主动点击上传或拉取时才访问云端，首版不做后台自动同步。

云端同步以下投资域数据：财务档案、目标、持仓、决策与决策复盘、决策内冻结的规则检查、AI 分析历史、周期复盘、投资规则及修订历史、研究证据、组合检查点及其冻结持仓，以及不可变组合流水。

以下数据永不进入同步包：

- 模型 API Key；
- 行情 API Key；
- 模型提供商、模型名称和 Base URL；
- 云端 Access Token 与 Refresh Token；
- 云端地址与 Publishable Key；
- 端到端加密恢复密钥。
- 本机复盘提醒开关与去重状态。

模型密钥、行情密钥、账户令牌、同步恢复密钥使用不同的系统钥匙串条目保存；恢复密钥还按账户 ID 隔离。用户密码只从本地服务直接发送给账户提供商，不落盘。

## 同步协议

1. 本地数据库按固定白名单导出带类型的数据表快照。
2. 对快照内容计算 SHA-256，导出时间不参与内容指纹。
3. 使用随机生成的 256 位恢复密钥和 XChaCha20-Poly1305 加密；固定协议版本作为附加认证数据。
4. 云端只保存密文、随机数、内容指纹、结构版本和单调递增的 revision。
5. 上传通过数据库函数对 `expected_revision` 做原子比较并写入。版本不一致时停止同步。
6. 拉取先完成认证解密、结构白名单、记录数量、字段长度、数字有效性和内容指纹检查，再在单个 SQLite 事务中替换投资域数据。

当前同步数据结构为 v9：v6 为持仓与组合流水加入汇率来源和观察日期，v7 增加不可变流水冲正关联，v8 增加用户管理的长期记忆偏好与注释，v9 增加持仓证券价格估值证据。客户端能够读取和恢复 v1–v8 数据包：v1 不包含组合检查点；v1/v2 持仓没有估值日期和折算汇率；v1–v3 不包含组合流水；v4 流水没有导入标识，恢复时按手工记录处理；v5 的汇率没有来源和观察日期；v6 没有冲正关联；v7 没有长期记忆偏好；v8 没有证券价格估值证据。恢复旧包后，缺失字段会在本机安全降级为用户声明市值。新版客户端下一次成功上传会以新的 revision 写入 v9 包。密文外层版本与解密后数据版本不一致时，恢复会被拒绝。

恢复密钥没有上传到云端。新设备必须从另一台设备导出并手动导入；密钥丢失后，服务运营方也无法恢复密文。改名前生成的 `zhiheng-sync-v1:` 恢复密钥与旧加密包仍可读取，导入或再次上传后会规范化为 `mario-sync-v1:`，避免品牌迁移造成数据不可恢复。

## 冲突策略

首版不使用“最后写入者获胜”，也不自动合并投资记录：

- 云端 revision 高于本机同步基线时，上传被拒绝；
- 本机与云端内容不同，拉取需要用户明确确认替换；
- 模型配置、模型/行情密钥和账户配置不会在拉取时被替换；
- 完整快照能够表达本地删除，无需首版引入墓碑记录。

后续如果升级到逐对象同步，应给决策原始记录、复盘记录和规则修订定义不同的合并语义，不能使用一个通用的字段级合并器。

## Supabase 参考部署

1. 创建 Supabase 项目，按产品需要配置邮件确认和自定义 SMTP。
2. 执行 [`server/migrations/supabase-cloud-sync.sql`](../server/migrations/supabase-cloud-sync.sql)。
3. 客户端“账户与同步”页面填写项目 URL 与 Publishable/anon Key。
4. 创建账户、完成邮件确认并登录。
5. 首次上传后立即导出恢复密钥，离线保管。

若确认邮件未收到或已过期，可在“账户与同步”页面重新发送。确认链接由 Supabase 托管；即使验证完成后浏览器最终跳到未启动的 localhost 页面，也可以直接返回 mario 使用原密码登录。常见的“邮箱未确认”“邮箱或密码错误”和发送频率限制会转换为可操作的中文提示。

数据库表启用 RLS；`anon` 无表权限，`authenticated` 只有按 `auth.uid()` 读取自己的密文权限。写入只能通过带 revision 比较的安全函数执行。生产环境还应配置备份、审计、速率限制、邮件投递监控和密钥轮换流程。

为调试包预置公开客户端配置时，可以在构建进程中设置 `VITE_SUPABASE_URL` 和 `VITE_SUPABASE_PUBLISHABLE_KEY`。首次启动会把两者写入本机配置；已有用户配置优先，不会被构建值覆盖。Publishable Key 本来就会随客户端分发，真正的安全边界必须由 RLS 和数据库函数建立；不要以任何形式把 Secret 或 `service_role` Key 放进客户端构建。

也可以使用官方 Supabase CLI 部署并执行真实的双设备加密同步测试：

```bash
supabase login --name mario
supabase db query --linked --project-ref <project-ref> \
  --file server/migrations/supabase-cloud-sync.sql
cargo build --manifest-path server/Cargo.toml
npm run supabase:test -- <project-ref>
```

测试会创建一个不发送邮件的临时已确认用户：设备 A 写入带唯一标记的数据并上传，设备 B 导入恢复密钥后拉取；随后检查云端密文不包含明文标记，并删除临时用户、级联密文和本机测试凭据。脚本只把敏感 Key 保存在权限为 `0600` 的临时文件和进程内存中，不打印或写入仓库。日常客户端只配置 Publishable Key，绝不使用 `service_role`/Secret Key。

## 可替换边界

服务端的账户与对象存储调用通过 `CloudSyncProvider` 抽象。Supabase 是首个实现，自托管服务只需实现注册、登录、令牌刷新、读取密文和原子版本写入，不需要接触明文投资数据。
