# 2026-11-07 测试构建产物绑定核查

## 基线与问题

本轮接续模块 spec 对齐，开始时 `main` 与 `origin/main` 均为 `fdd30dd`，工作区干净。实现与独立复核分别由测试、后端角色承担，主负责人统一维护规范、执行验收、清理与交付。

上轮保留的[验证入口缺口](team-review-20261107.md#后续验证事项)仍存在：完整门禁的 Cargo 构建尊重 `CARGO_TARGET_DIR`，HTTP／Web／桥接／备份／启动验收却多处固定读取 `server/target/debug`；继承的 `MARIO_TEST_SERVER_BIN` 还可能使完整门禁启动另一份旧程序。默认环境通过不代表自定义 target 或仓库外调用时验收的是本轮产物。

另经独立复核确认：加密备份验收直接启动 API，未处理的 ENOENT／EACCES 事件可能使 Node 跳过 `finally`，临时 PostgreSQL 留存；未成功 spawn 的 child 若仍等待 `exit`，清理也可能挂起。这是已有失败路径缺口，本轮一并处理。

## 修复边界

- [共享产物定位](../../scripts/server-artifacts.mjs)集中定义仓库根、Cargo target 和本机 debug 程序；相对 target 按仓库根解析，空白使用入口默认值，非空路径保留原文，Windows 程序加 `.exe`。
- [完整门禁](../../scripts/test.sh)先固定仓库根，再清除外部二进制覆盖并发布明确绝对 `CARGO_TARGET_DIR`，使 Cargo 和其后验收选择一致；Cargo 全局配置不能让本次构建漂移到另一目录。独立验收仍保留显式二进制覆盖，来源应由调用方负责确认。
- [财务门禁](../../scripts/test-financial.mjs)将迁移测试、Cargo 构建、HTTP 的 target 一起绑定；有指定 target 时复用，未指定则保持独立 `.runtime/financial-build`，不接受继承的旧测试二进制替代自身构建。
- 功能 API、Web、托管 HTTP、桥接、备份、启动测试复用产物选择；[本机源码启动器](../../scripts/codex-bridge.mjs)显式构建并启动同一 target，保持已有模式／站点参数校验，不增加新 CLI 功能或读取登录信息。
- 备份验收提前检查程序，并将实际 spawn 失败转为可清理的异常；清理跳过从未成功启动的 child。测试只使用临时程序、目录或数据库，不触碰部署和开发集群。
- 同步[验证规范](../module-boundaries.md#开发流程)、[文档索引](../README.md)、[Web 构建](../client-builds.md)、[桥接](../codex-bridge.md)和[备份验收](../data-migration.md#验证)。Web 文档另外清除上轮遗漏的 CSV 导入及复盘到期事项旧描述；当前交互分别由账号 JSON、证据附件和复盘分类承担。

## 验证设计与结果

[Node 回归](../../scripts/server-artifacts.test.mjs)覆盖路径、环境和构建型入口的实际子进程调用。主验收从仓库外执行完整门禁，使用全新相对 target `.runtime/test-entry build`（含空格），并故意提供不存在的 `MARIO_TEST_SERVER_BIN`、错误的功能测试站点与令牌。只有入口正确固定根目录、忽略不属于本次构建的覆盖并保持临时服务隔离，整条门禁才能通过。

从仓库外调用完整门禁脚本以退出码 0 通过：架构检查与 10 项边界测试、21 项 Node 回归、研究工具与部署脚本测试、前端构建／格式／331 项组件测试、Rust 格式／Clippy／构建／315 项测试（另 6 项真实模型或外网测试按既有配置忽略）、临时库中的 Web／API／默认桥接和财务门禁均通过。财务门禁对原生恢复的 296 张表逐表比对一致，迁移测试、构建和 HTTP 确实使用含空格的同一 target。

独立 `test:startup` 和 `test:codex-bridge -- --protocol-fixture` 也已通过：调用时把 Cargo target 设为一个不存在的目录，同时显式指定本轮程序，验证独立 binary 覆盖仍有效。协议夹具启动真正的桥接 worker 和本地假 App Server，覆盖 503 恢复、额度失败及已有输出不重放，不登录或调用真实模型。

加密备份首轮在公共分红恢复断言失败。核查发现该测试把模拟来源日期写死为 2026-11-05，而同提交程序内置资料已更新到 2026-11-07；按既有 `(asOf, fetchedAt)` 新旧规则，API 初始化应以较新资料更新旧记录。测试因此未正确构造“比内置资料更新的抓取快照”，不能据此认定加密包丢失数据。夹具已从源库实际初始依据派生严格更晚的采集时间，保留精确金额、来源和全文相等断言，不改恢复器或资料新旧规则。真实 `test:backup` 重验通过，随后按独立复核建议补上源库写入后及第二次离线覆盖恢复后的全文断言，最终再次通过完整加密备份验收；首次恢复同时在目标 API 启动前后核对全文，区分归档恢复与初始化。测试涵盖密码和篡改拒绝、密钥恢复、会话撤销、配置保留、SQL 回滚、反复覆盖、孤立账号清理与安全备份回退；相关 Node 21 项回归复查也通过。该夹具只验证同一版本内置 seed 不覆盖较新的恢复资料，不阻止未来版本或来源带来的合法新事实。

全部验证结束后，确认本轮 target 的绝对路径与二进制无人占用，执行 `cargo clean` 清理 `.runtime/test-entry build` 的 3.2 GiB 产物并确认目录已删除；独立覆盖使用的不存在 target 也没有被创建。测试临时集群与夹具由各入口清理。没有清理主工作区已有服务、开发数据库或其他任务的编译目录。最终检查通过：6 份本轮文档的 245 个本地目标／锚点均有效，17 个改动文件均属于本轮范围；JavaScript 语法、Bash 语法、冲突标记及 `git diff --check` 通过。

## 保留的边界

本轮不改账号业务、数据库 schema、模型授权或策略。默认桥接验收与 `--protocol-fixture`、整站加密备份独立验收是否接入默认完整门禁，继续按各自当前规范说明；不把一次显式运行冒充默认覆盖。没有执行部署、真实 OAuth 或付费模型推理，不停止其他服务或清理其他工作树。
