# benchmark v2 行动指南：二十年红利与科技股、宽基指数

本文是 v2 的规划与待决事项，不描述已实现行为。当前已实现的 v1 契约、采集命令与限制以 [benchmark](benchmark.md) 为准；各阶段落地后，把长期有效的部分合入该文档并删除本文中已完成的段落。

## 1. 结论先行

值得做，但要先想清楚它能回答什么问题、不能回答什么问题。

- **能回答**：Agent 能否在只看到当时已公开信息的前提下，正确读取财报、给出可核对的事实，并做出排序或仓位决策；不同方法论版本与确定性规则之间的相对优劣；策略在不同市场阶段（2008 危机、2015 股灾、2018 熊市、2020–2021 结构牛、2022–2024 下行、红利行情）是否稳健。
- **难以回答**：LLM Agent 在历史上“真的能赚多少钱”。主流模型的预训练语料已经包含 2006–2024 年的行情结局，按日期截断输入无法消除这种记忆。历史回测得出的超额收益，对 LLM 而言天然偏乐观。
- **因此采用双轨设计**：二十年历史数据主要用于（1）确定性因子与规则的研究和回测，（2）Agent 读取、抽取、推理能力的评测，（3）记忆污染程度的测量；真正检验 Agent 选股或配置能力，依靠模型训练截止日之后的**前瞻留出集**，从现在起按季度滚动累积。
- **样本量有限**：20 年、按季度决策只有 80 个决策期，63 日窗口相互独立的样本更少。每次修改提示词并查看结果都消耗一次“试验”，必须记录全部试验并限制测试集的打开次数，否则很快就会过拟合到历史。

## 2. 与 v1 的差异

| 维度 | v1（已实现） | v2（本计划） |
| --- | --- | --- |
| 时间 | 2016–2025，2015 预热 | 2006–2025，2005 预热 |
| 股票池 | 中证红利历史成分中按上年末总市值前 20 | 红利池 + 科技池，均按时点选样，保留已退市公司 |
| 宽基 | 5 只 ETF 日线 | 指数日线点位为主，ETF 只从实际上市日起作为可投资对照 |
| 财报 | PDF 原件与元数据，`metrics` 可空 | 增加结构化财务指标、分红送配事件账本 |
| 评测 | Rank IC、top-k 收益代理 | 增加 Agent 任务集、含成本的组合回测、污染测量、前瞻留出集 |
| 分发 | 本地构建，未上传 | Hugging Face 私有仓库，固定 revision |

v1 的核心约束全部保留：`available_at <= cutoff` 的时点截断、原始/修订版本分离、标签与输入分开、缺失不前向填充、不可覆盖的发布目录、内容哈希清单。

## 3. 范围决策（2026-10-31 已确定）

以下决定在 P0 写入新的 `benchmark/config.json` 版本。

1. **市场范围**：只做 A 股。v1 的采集链路、巨潮财报来源与时点规则都能复用。美股（SEC EDGAR 的财报与 XBRL 结构化数据免费且可再分发）留作 v3 扩展，避免币种、会计准则和交易制度同时变化。
2. **科技股池**：每年按上一年末总市值，在当时有效的申万一级“电子、计算机、通信、传媒”行业中取前 20。行业归属必须按时点；申万分类在 2014、2021 年两次调整，必须用当时版本，不能用今天的行业标签回溯。
3. **红利池**：从 2008 年开始（中证红利 2008-05-26 正式发布），科技池从 2006 年开始。2008 年前不做规则化补齐。
4. **数据来源**：先只用免费来源跑通 P1–P5 小切片流程，再评估是否引入 Tushare 来规模化、补齐缺口。免费来源取不到的数据如实记为缺口，不用当前数据回填历史。
5. **分发**：Hugging Face 私有数据集仓库 `mario_bench`，以后再考虑公开配方版。

宽基清单：上证50（2004 发布）、沪深300（2005）、中证500（2007）、中证1000（2014）、创业板指（2010）、中证红利（2008）、科创50（2020）。发布日之前的点位属于指数公司回测，数据中用 `backfilled=true` 标出，评测时不当作可投资基准。

### 免费来源下的已知难点

以下三项最依赖授权数据源，小切片阶段先验证免费路径能否满足，结论决定是否引入 Tushare：

- **中证红利历史成分**：从指数公司官网的历次调样公告与初始成分逐期重建，每期核对候选数量。
- **申万行业时点归属**：寻找申万宏源历次分类调整的公开文件；取不到可靠的时点归属时，记录缺口，不用当前行业标签回溯。
- **历史总市值**：用未复权收盘价乘以当时总股本计算，总股本取自已披露财报或股本变动公告，并保留出处；股权分置改革期间需核对是否包含非流通股。

## 4. 数据层规划

### 4.1 来源与覆盖

| 数据 | 首选来源 | 二十年覆盖风险 | 处理方式 |
| --- | --- | --- | --- |
| 股票日线、复权因子 | Tushare（授权）；腾讯/Yahoo 免费作对账 | 2006–2010 部分小票缺日、停牌多 | 保留原始价与复权因子两套口径；停牌须有交易所停复牌出处 |
| 指数日线点位 | 中证指数、交易所；Tushare `index_daily` | 基日前为回测值 | 标注 `backfilled`；记录发布日 |
| ETF 日线 | 同 v1 | 只有上市后数据 | 不用指数伪造 ETF 历史 |
| 历史成分与行业 | Tushare 指数成分、申万行业成分（带纳入/剔除日） | 免费来源基本没有 | 对照指数公司调样公告抽样核对，`membership_verified` 只在核对后置真 |
| 财报原件 | 巨潮资讯 | 2006–2008 部分公告标题格式不一、存在扫描版 PDF | 复用 v1 的 `collect-public` 与 `repair-catalogs`；扫描件标记为需 OCR |
| 结构化财务指标 | Tushare 财务三表（含公告日与更新标记） | 早期修订记录不全 | 只取首次披露版本；抽样与 PDF 对账 |
| 分红送配 | 巨潮分红公告；Tushare `dividend` | 早期送转比例口径混杂 | 建事件账本：预案日、股权登记日、除权日、派现与送转比例 |
| 退市 | 交易所退市公告 | 科技股退市较多（如乐视网） | 退市当期标签按最后交易价或清算结果计算，不能记为缺失后丢弃 |

### 4.2 二十年跨度特有的坑

- **幸存者偏差**：只拿今天仍在交易的公司向前回溯，会系统性高估收益。股票池必须来自当年时点的候选全集，已退市公司的数据全部保留。
- **会计口径断点**：2007 年新会计准则、2018–2019 年新金融工具准则（银行先行）、2020 年新收入准则。结构化指标中记录所用准则，跨断点的同比计算需要标注，Agent 输入中也要说明。
- **股权分置改革**（2005–2007）：大量公司在此期间有对价支付，复权因子与总股本变化剧烈，选样用的总市值要核对是否含非流通股。
- **涨跌停与停牌**：2015 年千股停牌、千股跌停。组合回测必须实现涨跌停不可成交和停牌不可交易，否则 2015、2016 年的回测结果失真。
- **银行与非金融企业**：财务科目不可比，红利池里银行占比高。指标按行业模板分开，不直接混排。

### 4.3 规模估算

v1 的 100 家公司 10 年共 4371 份 PDF、约 11 GB。v2 两个股票池按年取前 20，二十年的公司并集预计 120–200 家，财报 PDF 预计 25–45 GB，日线约 100 万行。数据量本身不是瓶颈，瓶颈是成分核对、财报版本核对和指标对账的人工工作量。

## 5. 任务层规划：用 benchmark 优化 Agent

数据集只是原料，Agent 优化需要明确的任务、指标和试验纪律。

### 5.1 任务类型

| 任务 | 输入（按决策时点截断） | Agent 输出 | 评分 |
| --- | --- | --- | --- |
| A. 财报事实抽取 | 单份财报的若干页原文 | 指定科目数值、单位、累计/单季口径 | 与结构化指标逐项比对的准确率；考察引用和口径 |
| B. 季度横截面排序 | 股票池的事实卡（财务指标、分红记录、价格动量、估值） | 每只股票的分数 | Rank IC、top-k 超额收益（沿用 v1 评测） |
| C. 组合配置 | B 的输入 + 宽基点位 + 当前持仓 | 目标权重与现金比例 | 含成本、涨跌停、停牌约束的组合回测：超额收益、最大回撤、换手 |
| D. 风险识别 | 财报与公告 | 分红可持续性、盈利质量等风险标记 | 与之后真实发生的事件（削减分红、业绩大幅下滑、ST、退市）比对的命中率与误报率 |

建议顺序是 A → B → D → C。A 的答案客观，最先暴露数据与提示词问题；C 最接近真实使用，但噪声最大，应在其他任务稳定后再做。

### 5.2 基线

每个任务都要有不调用模型的基线，Agent 只有稳定超过基线才说明提示词有效：等权持有股票池、沪深300、按股息率排序、v1 动量、简单质量因子（ROE 稳定性 + 负债率 + 分红连续性）。确定性基线同时是确定性规则研究的产出，表现好的规则可以沉淀到 mario 的 `planning`、`risk` 等确定性模块，比提示词更可靠。

### 5.3 记忆污染测量

同一批样本跑两种输入：真实公司名称与代码，以及匿名化版本（名称、代码替换为随机标识，日期整体平移，金额按比例缩放）。两者表现差距越大，说明模型越依赖对历史结局的记忆。匿名化不能完全阻止识别（特定财务数字仍可能被认出），因此它只用来估计污染程度，不能把匿名化后的历史成绩当作真实能力。

### 5.4 试验纪律

- 训练/验证/测试按时间切分，沿用 v1 的思路并扩展到二十年，例如 2006–2017 训练、2018–2021 验证、2022–2025 测试；切分写入配置，改变切分即新版本。
- 每次试验登记：方法论正文哈希、工作流版本、模型标识与参数、数据集 revision、任务与切分、结果。登记文件只追加不覆盖。
- 只在训练、验证集迭代；测试集只在锁定一个候选版本后打开一次，结果无论好坏都记录。
- 报告结果时同时给出试验总次数，避免只展示最好的一次。
- **前瞻留出集**：从 2026 年第四季度起，每个季度末用当时数据生成一次决策并冻结存档，季度结束后再评分。这是唯一不受模型记忆影响的检验，也是最终是否采纳某个策略的主要依据。

### 5.5 成本控制

任务 B、C 每个决策期一次调用，输入为事实卡（每家约数百字），全量 80 期约数百万 token，可承受。任务 A、D 若每家每期读整份财报（年报常超过 200 页），调用量和 token 会高出两个数量级，应只在抽样子集上做，并使用预先抽取的相关章节而不是整份 PDF。

## 6. 与 mario 现有架构的衔接

遵守 [架构说明](architecture.md) 中“离线 benchmark 研究工具”一节：`benchmark/` 不导入前后端源码、不访问 PostgreSQL 或账号数据、不读取生产凭据，在线服务不调用研究 CLI。

- **Agent 评测运行器**放在 `benchmark/` 内，作为新模块（如 `agent_eval.py`），读取发布包 inputs，调用模型提供方，输出与 v1 相同格式的预测文件后交给 `evaluate`。模型凭据只从终端环境变量读取，与 v1 的 `TUSHARE_TOKEN` 规则相同。
- **方法论作为被优化对象**：运行器把一份方法论正文作为参数传入。mario 中用户可编辑的方法论（见 [投资方法论](methodology.md)）可以导出为文件参与评测，评测结论再由用户决定是否写回，不由脚本自动修改账号数据。
- **确定性规则的沉淀**：benchmark 中验证有效的规则，按 [模块边界](module-boundaries.md) 的扩展步骤进入 `server/src/` 的领域计算模块，有单独的测试与设计说明，不直接搬运研究脚本。
- **不复用在线工作流 v8 的输出契约**：v8 面向个人财务问答（回答、建议、事实引用），benchmark 任务需要分数或权重。若以后要评测完整的在线工作流，需要另行设计“benchmark 冻结输入”契约，并按 AGENTS.md 先给出设计再实现。

## 7. Hugging Face 托管方案

### 7.1 授权是硬约束

公开可浏览不等于允许再分发。v1 已记录 `redistribution_status=not_reviewed`，v2 必须逐项确认：

| 内容 | 再分发风险 | 建议 |
| --- | --- | --- |
| 巨潮财报 PDF | 上市公司依法公开的信息，但网站有使用条款 | 公开仓库只放 URL、SHA256、元数据和下载脚本；PDF 仅放私有仓库 |
| 指数点位与成分 | 中证指数、深证信息对指数数据有版权与授权许可 | 不公开再分发原始点位和成分权重 |
| Yahoo/腾讯行情 | 服务条款通常禁止再分发 | 不上传原始行情；公开版只放衍生标签或由用户自行采集 |
| Tushare 数据 | 受其用户协议约束 | 按协议条款处理，默认仅私有使用 |
| 自建内容 | 任务定义、评测代码、Agent 预测、试验登记 | 可以公开，选择合适的开源许可证 |

结论：**先建私有数据集仓库**，完整内容只在私有仓库中使用；如果以后公开，发布“可复现配方”版本：元数据、哈希、任务定义、评测代码和采集脚本，使用者自行下载原件和行情后用 `verify` 校验一致性。

### 7.2 仓库结构

```text
<账号>/mario_bench（私有，dataset）
├── README.md                  数据集卡：范围、选样规则、时点规则、已知缺口、授权状态
├── universe/                  年度候选全集与选中名单（红利池、科技池）
├── prices/                    股票、指数、ETF 日线（含口径与来源字段）
├── reports/                   财报元数据（版本、披露与可用时间、哈希、URL）
├── financials/                结构化指标（首次披露版本）
├── corporate_actions/         分红送配与退市事件
├── documents/<sha256>.pdf     原件，内容寻址
├── tasks/<任务>/{train,validation,test}.jsonl
└── manifest.json              逐文件哈希
```

测试集标签与前瞻留出集标签放在**另一个**私有仓库 `mario_bench_labels`，评测时单独授权读取，降低意外泄漏和被未来模型训练语料收录的风险。数据集卡中加入唯一的 canary 字符串，便于以后检测模型是否见过本数据。每次评测结果记录所用的 Hugging Face commit SHA，数据更新只发布新 revision 并打标签，不修改已发布的 revision。

上传使用 `huggingface_hub`（或 `hf` CLI）从本机执行，token 只放在本机环境，不写进仓库或配置文件。上传脚本属于发布环节，与 v1 “研究模块只用 Python 标准库”的约束冲突时，把上传隔离为单独的可选命令和依赖说明，不让采集、构建、评测模块依赖第三方库。

## 8. 分阶段计划与验收

| 阶段 | 内容 | 验收标准 |
| --- | --- | --- |
| P0 范围定稿（约 1 周） | 拍板第 3 节决策；确认 Tushare 权限；核对授权条款；起草 v2 配置与数据集卡草稿 | 配置文件与本文更新；授权结论逐项有出处 |
| P1 时点股票池 | 红利池、科技池逐年候选全集与选样；退市公司元数据 | 每年候选数量与官方名单一致；抽样 3 个年份对照调样公告；`membership_verified` 有核对记录 |
| P2 行情与指数 | 股票池并集的 2005–2025 日线、复权因子、停复牌；7 个宽基指数点位；ETF 上市后日线 | 与交易日历逐日对账；剩余缺口逐条有说明；两套价格口径不混用 |
| P3 财报与指标 | 财报原件扩到二十年；结构化指标；分红送配账本 | 报告期覆盖率报告；每类行业抽样不少于 30 个指标与 PDF 对账；扫描件清单 |
| P4 发布 v2 | `validate/build/verify` 生成不可覆盖发布包；上传私有仓库 | 下载后 `verify` 通过；数据集卡写明已知缺口与授权状态 |
| P5 任务与基线 | 任务 A、B 及确定性基线；组合回测（成本、涨跌停、停牌、退市） | 基线结果可复现；回测规则有合成数据测试 |
| P6 Agent 评测与迭代 | 评测运行器、试验登记、记忆污染测量；在训练、验证集迭代方法论 | 每次试验有登记；测试集只打开一次并记录 |
| P7 前瞻留出 | 每季度末冻结决策，季度后评分 | 连续多个季度的结果与历史测试结果对比 |

P1 到 P3 是工作量最大、最需要人工核对的部分。建议先用一个小切片（例如 2008、2015、2021 三个年份，红利池与科技池各前 5 家）打通 P1–P5 全流程，确认契约和评测可用，再铺开到二十年全量。

## 9. 主要风险

- **记忆污染**：历史成绩高估 Agent 能力。对策：污染测量、前瞻留出集为最终依据。
- **过拟合**：样本少、迭代多。对策：试验登记、测试集只开一次、报告试验次数。
- **数据核对工作量**：成分、版本、指标对账依赖人工。对策：小切片先行、抽样核对、缺口如实保留而非补造。
- **授权**：公开再分发可能违约。对策：私有仓库、公开版只发配方。
